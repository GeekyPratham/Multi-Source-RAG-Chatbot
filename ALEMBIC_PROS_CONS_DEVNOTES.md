# Alembic Integration: Pros, Cons & Development Notes

## Pros

- **Version Control**: Every schema change tracked in Git with clear audit trail
- **Reproducibility**: Same migration files produce identical schema across dev/staging/production
- **Rollback Support**: Each migration has `upgrade()` and `downgrade()` — can revert changes if needed
- **Autogeneration**: `alembic revision --autogenerate` reduces boilerplate and human error
- **Startup Safety**: App startup no longer executes DDL — only `SELECT 1` connectivity check
- **Audit Trail**: `alembic history`, `current`, `heads` provide schema state visibility
- **Team Collaboration**: Migration files shared via Git — no need to manually communicate SQL changes

## Cons / Trade-offs

- **Learning Curve**: Team must learn Alembic commands and workflow (`revision`, `upgrade`, `downgrade`, `stamp`, `check`)
- **Extra Step**: Migrations run as separate deployment step, not automatically on startup
- **Existing DB Complexity**: Must verify schema match before stamping or running migrations; blind `upgrade head` fails on existing tables
- **Downgrade Risk**: Destructive ops may lose data; downgrade is best-effort only
- **File Management**: Migration files accumulate; need regular review; merge conflicts must be resolved carefully

## Development Considerations

### Small-Scale (solo/small team, local dev)

- Install alembic (in requirements.txt)
- Modify models → `alembic revision --autogenerate -m "description"` → review → `alembic upgrade head`
- If tables exist, verify schema matches then `alembic stamp head`
- Memorize: `alembic revision --autogenerate`, `alembic upgrade head`, `alembic current`

### Large-Scale (CI/CD, multiple instances, team collaboration)

- Run `alembic upgrade head` as separate deployment step before code deployment
- Use deployment locks — only one runner executes migrations at a time
- Always back up production DB before migrations
- Review all migration files in PRs before merging; manually inspect autogenerated files
- Do NOT auto-downgrade on deployment failure; plan rollback separately
- DATABASE_URL from env vars/secret manager — never hardcode
- Monitor migration execution time/errors; long migrations can lock tables
- Feature branches should include migration files; resolve merge conflicts carefully

### Migration Workflow (all from backend/)

```bash
export DATABASE_URL="postgresql+asyncpg://user:password@host:5432/dbname"

alembic revision --autogenerate -m "description"
# review file...
alembic upgrade head
alembic current
alembic downgrade -1
alembic stamp head  # if schema already matches
```

### Production Deployment

1. Backup database
2. Run `alembic upgrade head` as separate CI/CD step
3. Deploy app code after migrations succeed
4. Never auto-downgrade on deployment failure
5. Use env vars for DATABASE_URL — never commit credentials

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| Existing tables fail CREATE TABLE | Verify schema; use `alembic stamp head` if matching |
| ENUM → VARCHAR truncation | Verify values fit in 50 chars |
| Downgrade data loss | Test in staging; treat as best-effort only |
| Concurrent migrations | Use deployment locks |
| Credentials in logs | DATABASE_URL from env only; check logs |
| Long migrations lock tables | Run during maintenance; test on staging |

## Manual Steps Required (database unreachable from this env)

1. Verify DB reachable from deployment env
2. Check if schema matches `001_initial_schema.py`
3. If tables exist & match: `alembic stamp head`
4. If tables need creation: `alembic upgrade head`
5. Test CRUD operations after migration
6. Add this file to `.gitignore`
